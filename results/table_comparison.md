# 调度策略对比结果（trace 驱动）

数据来源：Alibaba PAI cluster-trace-gpu-v2020（公开，sha256 已校验）。
每个 instance = 一个真实 6 小时繁忙窗口内的到达流 + 按 machine_spec 切出的真实机器分区。

关于 GPU 空闲率，本报告给出三个口径，因为它们会给出三种结论：

1. **固定窗口空闲率**：分母是模型时域的卡时。只要所有作业最终都跑完，已分配卡时就恒等于需求卡时，该值与策略无关（正好等于 1 − ρ），只能用来核对负载，不能用来评判调度质量。
2. **自身忙期空闲率**：分母换成该策略自己的 makespan，于是压缩 makespan 的策略会变好，但它奖励“早点收工”而与浪费无关，只作次级视角。
3. **带积压空闲卡时**：作业已经提交且仍在排队时，未被分配出去的 GPU 卡时。其中只有当某个排队作业在该槽位能同时放下它的 GPU/CPU/内存需求时，这份空闲才是调度器真正可以消掉的浪费，因此同时报告**总量**与**其中可利用**两项；表中的差值与所有图都使用“可利用”口径。队头阻塞制造可利用浪费，重排消除它，把作业推到时域之外会重新制造它。

## 多窗口 × 多种子稳健性扫描（08_sweep.py）

原研究的 6 个 instance 全部取自每个 pool **需求最大的那一个 6 小时窗口**、**一个**抽样种子。本节把同一套策略重放到 72 个 instance：窗口排名 1,2,3,median（rank1 = 最忙＝原窗口，median = 中位需求窗口，是选择性偏倚的对照）× 种子 [20261013, 20261103, 20261104] × pool ['P100', 'MISC'] × 3 个负载档。原研究的 6 个 instance 是这个网格的子集，因此充当内建阳性对照。

**种子这一维变的是作业集合本身，不是随机数标签。** 同一 (pool, 窗口排名, 名义负载档) 下 24 组、每组 3 个种子：实际达成负载 ρ 的组内最大/最小比中位数 1.19×（范围 1.00–2.22×），主机数也在 3–48 台之间变动。也就是说“同一档负载”在种子之间并不是同一个问题实例，这正是需要多种子的原因。

**阳性对照**：网格中 window_rank=1、seed=20261013 的那一格必须复现已提交的表格。54 行确定性策略（FIFO / EASY / 7 条优先级规则）与 `metrics.csv` + `metrics_priority.csv` 的最大相对偏差 = 1.48e-15（完全一致 = True）。12 行求解器策略的最大相对偏差 = 0.366——`milp` 以**墙钟**为限，同一 instance 在不同机器负载下可能落在不同 incumbent 上，这一偏差如实报告而不被断言掉。

机理是实测出来的，不是推断的。先写下过一个可被推翻的说法——「规则在这些格子里只是没东西可修」——回表逐个核 7 个低捕获格子，**该说法不成立**：其中只有 1 个的最佳规则平均等待与 FIFO 完全相同，其余 6 个其实胜过了 FIFO，只是远不及离线解。真正起作用的是另一半：离线 ILP 在 7/7 个格子里留下了**比规则更多**的积压空转，而它这部分空转的 40%–94%（中位 67%）属于「有空卡、队列里也有放得下的作业、求解器却没放」的可回收空转。贪心规则按定义做不到留卡——一有空卡它就把放得下的作业全启动。实测到此为止：能证伪的是「ILP 放弃了本可立即启动的作业、并因此拿到更低等待」。至于它为什么留卡（常见解读是预知后面的大 gang、攒够一次放行），模型不输出理由，只有排程，所以那是解读而不是结论。无论如何，未来信息是请求量优先规则原理上拿不到的，结论收窄成一句话：**规模优先替代的是滚动再优化，替代不了真正需要未来信息的离线最优。**
